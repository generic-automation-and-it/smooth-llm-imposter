# 00 - Cross-cutting decisions D1-D21

Status: normative. The other spec files cite these as "Dn". Where a later file states a detail more exactly (formulas, numbers, message text), that file is authoritative for the detail and this file for the intent.

Vocabulary: **bridge** translates a Claude Code Messages request to a Chat Completions request and the Chat reply back. **Client** is Claude Code. **Upstream** is the Chat-only provider.

| # | Decision | Detail in |
|---|---|---|
| D1 | `stop_reason`, stream and non-stream alike: `max_tokens` when the upstream stopped on length and no `tool_use` block survives; `tool_use` whenever at least one complete `tool_use` block is emitted, whatever the upstream finish reason; otherwise `end_turn`. A content-filter stop is `end_turn`. `stop_sequence` is never produced and its field is null. | 02, 03 |
| D2 | The reply echoes the **inbound model name** the client sent, never the upstream's model, never `unknown`. | 02, 03, 04 |
| D3 | The message id is synthesized (`msg_` plus 24 characters), unique per reply. Upstream ids are never exposed. | 02, 03 |
| D4 | Tool-call arguments are held per call until the call completes, then validated, then emitted as one delta. Empty becomes `{}`; one bounded repair (close unterminated strings and brackets only); still invalid means the call is dropped when the upstream stopped on length and otherwise the message fails with an `api_error`. Non-empty broken arguments are never replaced by `{}`. The `tool_use` block start is written only when the call is complete and valid. Numbers keep their textual form. | 02, 03 |
| D5 | Tool ids: keep the upstream id if it matches `^[a-zA-Z0-9_-]{1,64}$`; otherwise synthesize per 01-request-mapping.md:183 (request path, deterministic) and 02-response-mapping.md:174 (response path). Duplicate claimed ids append `_2`, `_3`, ... | 01, 02, 03, 04 |
| D6 | Tool names: sanitized to `^[a-zA-Z0-9_-]{1,64}$` with a hash-suffixed truncation, via a per-request map built from request tools and history, reversed on the reply; unknown names pass through. Stateless. | 01, 02, 03 |
| D7 | Upstream reasoning becomes thinking blocks with an empty signature; encrypted reasoning is dropped. History thinking blocks are dropped by default. Vendor profiles are chosen by an explicit provider option, never by host sniffing. | 01, 02, 03 |
| D8 | Usage: `input_tokens` excludes cache reads (and reported cache writes), floor 0; cache counters come from the accepted upstream field names listed in 02 (authoritative for the names); `output_tokens` is the completion count. Missing upstream usage is estimated with the shared estimator and `usage` is never empty. Streaming requests always ask for usage. `message_start` carries the request estimate, `message_delta` the final figures. | 02, 03, 04 |
| D9 | Keep-alive: a `ping` right after `message_start` and after every 8 seconds without a frame. `message_start` itself is written on the first upstream chunk, or after 8 seconds of upstream silence. | 03 |
| D10 | Every error leaves as the Messages envelope with the upstream status kept and a status-derived error type; the upstream message text is preserved; `retry-after` headers are forwarded. Context-overflow errors are re-phrased into the two forms the client is assumed to recognise (assumption — see 04 Open items). A stream failure, an in-band error object, or an end without a finish reason and without a terminator ends with an error event. An end after a finish reason is clean. | 02, 03, 04 |
| D11 | Empty upstream output is translated faithfully (empty content, mapped stop reason, real or estimated usage): no synthetic error, no retry. | 02, 03 |
| D12 | Text is never trimmed or re-joined except where a spec rule says so; whitespace is preserved. | 01, 02, 03 |
| D13 | Request field policy is an allowlist. Optimization and metadata fields without Chat meaning are dropped. Unsupported content blocks (documents, server-tool blocks, unknown types) become a one-line text placeholder. Typed server tool definitions in `tools` are rejected with HTTP 400 naming the tool; the tool-search server tool is dropped. In-sequence `system` messages are mapped, never rejected. `cache_control`, `output_config.format` and documents are governed by the provider options named in 01. Tool `strict` is forwarded verbatim whenever boolean per 01 section 8.2. | 01 |
| D14 | Tool results map to Chat tool messages that immediately follow the assistant message holding the matching calls, one per mapped call id (D5) in call order; orphan results become user text; calls without a result are kept. | 01 |
| D15 | Images map to image parts in user content; an image inside a tool result is hoisted into a user message right after that turn's tool messages, preceded by one text part naming the tool use. Images in assistant turns are dropped. | 01 |
| D16 | Not implemented by design: Files, Batches and skills-container APIs, cache TTL controls, citations, PDF input (except PDF-as-image_url under `documentMode: image`), server tools, fine-grained tool streaming. The client sending them is handled per D13. | 01 |
| D17 | Router contract: the bridge runs only on matched imposter routes of an Anthropic-dialect provider whose `AnthropicUpstreamApi` is `chat_completions`. It receives the model-renamed Messages body and the inbound model name and returns a Chat body plus a request-derived context (tool-name map, request estimate, inbound model name, streaming flag). Provider-key redaction inputs stay with the router forwarder and never enter the bridge context. The reply side receives that context with Chat SSE lines or a Chat JSON string, and for failures the upstream status and retry headers. | 01, 04 |
| D18 | The first system block is dropped when it is the client's per-request attribution marker, which would otherwise defeat provider prefix caching. | 01, 04 |
| D19 | An output limit below 16 is raised to 16 (the client's startup probe sends 1; several Chat upstreams reject smaller values). | 01, 04 |
| D20 | On a bridged route the outbound header set is an allowlist (content type, accept, the managed credential, the router's session header); no caller header is relayed. | 04 |
| D21 | The bridge makes one upstream attempt, with no retry or fallback of its own; the client retries. Upstream timeouts remain the router's per-provider timeout. | 04 |
